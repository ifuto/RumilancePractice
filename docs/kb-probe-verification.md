# KB Probe Mod 徹底検証レポート（例外カテゴリ完全列挙）

対象: `kb-probe/`（クライアント Mod、他サーバーのノックバック係数実測用）
版: 0.3.1 → **0.4.0**（本検証の結果として実施した修正を含む）
検証日: 2026-09-30
検証方法: 全ソースコード読解（KbProbe / KbProbeMath / ServerStats / StatsStore / mixin 4+2 本）、
vanilla 1.21.1（yarn デコンパイル）との逐行照合、オフライン実測シミュレーション
`kb-probe/sim/KbProbeSim.java`（KbProbeMath + ServerStats の**本物のクラス**を
vanilla の正確モデルで生成した wire 値で駆動）、ECJ による構文・自己クラス整合チェック。

## 1. 測定原理の正当性（妥当性検証）

本 Mod の測定は次の仮定に立脚する。各仮定がなぜ正しいかをソース照合で確認した。

1. `EntityVelocityUpdateS2CPacket` はサーバーが決めた**最終速度**を周囲へブロードキャストする
   （同一 tick 内の複数段ノックバック合成は 1 パケットにまとまる）。クライアントは
   間をローカル再シミュレーションでつなぐため、パケット HEAD 時点のローカル速度との
   差分 = 「直近のサーバーイベントで実際に加えられた衝撃」。
2. vanilla 1.21.1 の melee ノックバックは最大 2 段:
   - 1 段目 `damage() → takeKnockback(0.4)`: `newV = oldV/2 + 0.4(1−r)`
   - 2 段目 `attack()`: ノックバックレベル `k`（疾走 +1.0 + `GENERIC_ATTACK_KNOCKBACK` 属性）
     が `k>0` のとき `takeKnockback(k·0.5)`（同 tick のため被害者はまだ接地扱い）
   - 合成結果（静止・接地の標的）:
     `Δh = (k>0 ? 0.2+0.5k : 0.4)·(1−r)`、`Δy = min(0.4, (0.2+0.5k)(1−r))`
   - `KbProbeMath.expectHorizontal/expectVertical` がこの式と一致することを数値検証済
     （sim シナリオ 1-3: k=0/1, r=0/0.4 で f=1.000 ちょうどが返る）。
3. wire 値は `int = (int)(velocity × 8000)`（`.` 0.3.1 修正済。旧 0.3.0 は unscale 漏れで
   全サンプルが外れ値ガードに除去され「計測しているように見えて何も記録しない」状態
   だった → sim シナリオ 4 で再現・証明）。
4. 係数推定は `fH = 実測Δh / 期待Δh`、`fV = 実測Δy / 期待Δy` の算術平均。
   「最終ベクトルへの一括乗算」を行う実装（本家プラグイン含む）では fH=fV=係数が
   そのまま復元される。

## 2. 検証で特定した欠陥（修正済み）

### 2.1 【致命】出荷版 0.3.1 はコンパイル不能（集計チャット部）

`ServerStats` は Gson でそのまま永続化するため全フィールドが **public フィールド**
（`public int hSamples`）だが、`KbProbe.announceSample` が `stats.hSamples()` と
**メソッド呼び出し形式**で参照していた。メソッドは存在しないため、0.3.1 ソースは
ビルドが通らない状態だった（リファクタリング中の取りこぼし）。
→ フィールド参照に修正（0.4.0）。教訓: 最終ビルドが手元で行えない環境下でも、
「自分のクラス間の参照整合」は必ずオフラインで機械検査する（後述 §6）。

### 2.2 【潜伏】警告通知が永久に出ない（オーバーフロー）

`lastNoKbNotice = Long.MIN_VALUE` 初期化。`clientTick − MIN_VALUE` は符号反転で
**負値にオーバーフロー**し、`< NOTICE_COOLDOWN` が常に真 → 「KB無効領域」
「攻撃不成立」のチャット通知が実運用で一度も表示されなかった
（統計カウンタは回っていたため、集計行の「※KB無効領域N回検出」だけは出る）。
→ `-NOTICE_COOLDOWN` 初期化に修正（0.4.0）。

## 3. 例外カテゴリの完全列挙（「数えてはいけない」もの）

ユーザーの要求である「ダメージ無効以外にも数えてはいけないケース」を洗い出し、
各カテゴリへの対処を実装した。凡例:
✔0.3.1 既存ガード / ✚0.4.0 新規対策 / ◆記録のみ（設計上やむを得ない既知限界）。

### 3.1 時間窓・成立系

| # | 例外 | 徴害 | 対処 |
|---|------|------|------|
| E1 | ダメージ成立パケットが来ない（保護領域・無敵中の殴り） | 速度の変化原因が特定不能 | ✔ 確認なし窓切れ → 計測せず noDamageEvents |
| E2 | ダメージは成立したが速度パケットが来ない（KB無効ロビー） | 係数 0 の誤登録 | ✔ velocity 未着窓切れ → 係数に記録せず noKbEvents ＋警告 |
| E3 | **パケット順序逆転**（velocity が damage より先着。tick 境界・リージョン跨ぎで起こる） | E2 の**偽陽性**（実際には KB 有効なのに無効領域と警告） | ✚ `velocityBeforeConfirm` フラグで「静かに破棄」に分離 |
| E4 | 対象が窓内に**即時テレポート**（kill/respawn、TP、スキルワープ） | 速度が届かず E2 偽陽性 | ✚ `EntityPositionS2CPacket` 捕捉で保留を静かに破棄 |
| E5 | 対象が窓内に**除去**（卸載・切断・リスポーン置換） | 同上＋E1 偽陽性 | ✚ `EntitiesDestroyS2CPacket` 捕捉で保留を静かに破棄 |
| E6 | 対象の**死亡（トーテム含む）** | キル後の速度は別実体挙動 | ✚ E4/E5 の経路で実質カバー（respawn 置換時） |
| E7 | **第三者の同時攻撃**（混戦。合成速度は最大 +100% 偏り、外れ値 2.5 に届かず素通りし得た） | 係数平均の直接汚染 | ✚ 窓内ダメージパケット 2 発以上で contaminated → 除外＋`contaminatedEvents` 集計表示 |
| E8 | **環境ダメージ**（落下・炎・棘）が窓内に割り込む | E7 と同型の confirm 汚染 | ✚ E7 の contaminated 判定で副次的にカバー |
| E9 | サーバー到達拒否の空振り（reach 判定・lag） | E1 カウンタのみ汚染（係数には混入しない） | ◆ クライアントから区別不能。ホワイトしない設計の既知限界 |

| # | 例外 | 徴害 | 対処 |

## 4. 0.4.0 で追加した防御の実装場所

- `KbProbe.onAttack`: E10（shield）・E11（GameMode）・E16（mace/smash）ゲート
- `KbProbe.onDamageConfirmed`: E7/E8 — 保留中のダメージパケットを `damagePackets++` し
  2 発以上で `contaminated = true`
- `KbProbe.onVelocityPacket`: E3 — 確認前の窓内 velocity を `velocityBeforeConfirm` に記録
- 新規 mixin `PositionTeleportMixin`（`onEntityPosition` → E4）、
  `EntitiesDestroyMixin`（`onEntitiesDestroy` → E5/E6）
- `KbProbe.recordSample`: E7（contaminated 除外）・E20（再接地＋妥当域）
  — 判定部は `KbProbeMath.verticalFactorPlausible`（MC 非依存・sim 共有可能）
- `KbProbe.onClientTick`: E3 — 窓切れ時に `velocityBeforeConfirm` なら noKb に数えず静かに破棄
- `ServerStats.contaminatedEvents`（新規、Gson 既存ファイルには既定値 0 で後方互換）
  — 5 件ごとの集計チャットにも `※混戦混入N回除外` を併記

## 5. 機械検証の結果

0. **超大量ファズ（2026-09-30 追加、`kb-probe/sim/KbProbeFuzzSim.java`）**: vanilla
   パイプラインを厳密複製（段ごとの `newV=oldV/2+strength*(1-r)`、接地のみ
   `min(0.4, vy/2+s)` の垂直、攻撃段 `0.5k` 合成、wire `(int)(v*8000)` 切捨て）し、
   mod 側の期待式・ガードと**独立 2 実装の突き合わせ**。乱数 20 万ケース
   （k∈[0,3], r∈[0,0.99], 攻撃方位 360°, 静止/微速/明確移動/空中、エッジグリッド
   + ジャンプ間隙 1 万件）の結果 **0 FAIL**。
   - 完全静止サンプル（式検証の本体）: H 平均ずれ 1.51e-3 / 最大 6.56e-2、
     V 平均 3.39e-4 / 最大 5.35e-2 — 最大値は r≈0.99 で期待値 0.004 級のときの
     wire 切捨てノイズ上限 (2/8000/expect ≈ 6.25%) と一致。**式は vanilla と一致**。
   - 低速移動（idle 閾値内）の受容サンプルも「複製側で ideal 2 回実行した厳密誤差
     エンベロープ」内に収束（旧速度の段複利半減混合 + 0.4 クランプ干渉を個々に評価）。
   - ジャンプ間隙の fV≈0 偽サンプルは妥当域で全件棄却。ガードの偽陽性もゼロ。
   - 教訓: 初版ハーネス自身の許容誤差モデル（単段 1/2 混合のみ・クランプ非考慮）が
     誤りであり、大量の疑似 FAIL で検出・修正した。期待値側を盲信しない構成が有効。
1. **シミュレーション**: `sim/KbProbeSim.java` を ECJ + JRE21 でオフライン実行。
   14 シナリオ（うち 12/13 は 0.4.0 新規のジャンプ間隙・外部インパルス混入）すべて Pass、
   `VERDICT: ALL SCENARIOS OK`。vanilla 正確モデルから生成した wire 値で水平/垂直とも
   f=1.000 が復元され、各ガードが期待どおり除去のみを行うことを確認。
2. **構文・自己整合**: mod 全ソースを ECJ に入力し、(a) 構文エラー 0、
   (b) 外部依存解決不能に由来しないエラー（自前クラス間の参照不整合）0 であることを確認。
   179 件のエラーはすべて net.minecraft / spongepowered / gson / fabricmc の import 解決
   （オフラインのため正当）。
3. **持久化の後方互換**: `kbprobe.json` の既存形式を変更しない（新フィールドは Gson で
   欠損→0 デフォルト）。`StatsStore` は tmp+atomic move 書き換えで破損耐性あり（変更なし）。

## 6. この検証から得た運用教訓（プロセス改善）

- **KB 計算本体は 1 行も変更していない**（ユーザー制約遵守）。上位（クライアント計測）側のみ。
- ビルドが手元で通せない環境では、「構文エラー 0」と「外部説明不能エラー 0」の
  **2 段構えスキャン**を標準化する（§2.1 のような出荷不能バグは自前クラス参照の
  整合チェックで機械的に捕えられる）。
- 新規テスト/シナリオは「件数が実際に増えたか」を確認して初めて有効
  （localtest の silent dep-drop と同じ罠。sim では scenario 追加後に pass 行数の増加を確認済）。
